## 2. 已实测的**硬约束**（会影响移植写法）

### 2.1 参数 schema：**默认值是空字符串的参数会被标成必填**

证据：`describe_toolset` 回的两份 schema 对比 ——

```
request_plan_change: properties={items_json, by(default "用户"), reason}
                     required=["items_json","reason"]          ← reason 的默认值是 ""
check_build_target : required=["decision","target_level"]      ← 两个的默认值都是 ""
get_plan           : properties={include_plan(default true)}   ← 没有 required
```

实测后果：`arguments:{}` 调 `check_build_target` 被拒 ——
`Function "check_build_target", input params are required by the function input schema Json,
but incoming function input params Json is empty.`
补上 `{"decision":"","target_level":""}` 就通了。

⇒ **写工具时不要用 `""` 当默认值**：要么给非空哨兵值，要么干脆不带默认值（老老实实必填）。

### 2.2 嵌套容器不支持 → 复杂入参收成 `str` 再 `json.loads`

（上一轮实测：`list[dict]` 之类会在**模块导入期**就报
`directly nested containers are not supported`，整个工具集一起死。）

### 2.3 返回值会再包一层 `{"returnValue": ...}`

`execute_tool` 的 `value` 是一串 JSON，里面还包着 `returnValue`。`call_official` 解这两层。

### 2.4 官方 void 工具成功后 `value` 可能就是空

不是失败。`call_official` 把它记成 `LAST_META["value_is_none"]=true` 并返回 `(None, "")`，
不拿它当错误（原来的文案"没有返回值"会让**成功**也被当失败）。

## 3. ⚠ 脚本通道（`ProgrammaticToolset.execute_tool_script`）在插件里**不能用**

实测（2026-10-11 17:57:57）：

```
probe_batch → {"ok": false,
               "error": "返回值不是 JSON: JSONDecodeError('Expecting value: line 1 column 1 (char 0)')",
               "meta": {"tool": "execute_tool_script",
                        "is_complete": false,        ← 没完成
                        "value_is_none": false,      ← 有个值，但是空的/不可解析
                        "seconds": 0.01}}
```

`is_complete=false` ⇒ **它是异步的**；而 toolset 方法跑在 game thread 上，**等不了**。

**但它本来就不需要存在**：`batch=true` 这条通道的唯一收益是**省 HTTP 往返**。
进程内 `execute_tool` 就是一次函数调用（实测 0.000~0.022 秒 / 次）——
**插件里直接用逐行循环就是最优解**，`execute_tool_script` 一概不用。

⇒ 附带好处：脚本沙箱那套 payload 双重 `json.dumps` 转义、`_SAFE_BUILTINS`、
以及 `[完工-22]` 那一类"脚本里引用丢了"的坑，**在插件这条路上全部消失**。

## 6. 已拍板的移植路线（2026-10-11 用户选择）

1. **异步**：选 **A · 事件循环垫片** —— 20 个工具入口保持 `async def`，
   外面套一个私有 `asyncio` 事件循环驱动；`await` 一行不删。
   *依据*：实测 19 次官方调用**全部当场完成**（`is_complete=true`），协程永远不会真的让出。
   ⚠ **前提待验**：`probe_asyncio()`（UE 自带 Python 里能不能 `new_event_loop()` 并在循环里真调官方工具）。
2. **pydantic**：选 **A · 写最小垫片** —— 只实现 `BaseModel`（`__init__` 走 kwargs + 默认值、
   属性访问）/ `Field(default, description)` / `model_dump()` / `model_copy(update=…)`。
   代价：类型校验没有了（实测产品不依赖它做控制流）。
3. **阶段三核心**：**做** `probe_stage3()` 探针（建 Actor → 加 cube → 进分组 → 删掉）。

### 10.1 ⚠⚠ 第 3 个机制性缺陷（最深的一个）：**官方工具报的错不在我们的 Python 帧里**

**现象**（实测原文）：

```
!! TOOL ERROR:  Folder does not exist: 'UEMCP_env'
```

**判据（很硬）**：返回文本里**没有** `官方工具 … 返回错误：` 那个前缀 —— 而那个前缀是
`call_official()` 里 `once()` 抛 `ToolError` 时**一定**会加的。⇒ **根本没走 ToolError 通道。**

**根因**（日志实测原文）：

```
[2026.10.11-11.42.32:635][692]LogScript: Warning: Folder does not exist: 'UEMCP_env'
```

官方 `get_actors_in_folder` 对**不存在的文件夹**不是回一个 `is_error` 结果，而是在 UE 那侧
记一条 `LogScript: Warning`，**MCP 层把这条当成整次调用的结果** —— 我们方法里**已经拿到的
成功返回值被覆盖**成 `isError`。

**后果（影响面比一个工具大）**：产品里所有"**捕获官方错误来容错**"的分支
（`except ToolError` + `"does not exist" in str(exc)`）**在插件里都不会触发**。
实测现场：`setup_environment(restore=true)` **回滚真的做完了，调用却报失败**。

**修法（预防，不是兜底）**：`get_actors_in_folder` 调用前先看文件夹在不在
（`get_folders` + 2 秒缓存，`set_actor_folder` 成功即作废缓存）；不在就**自己合成**
`"Folder does not exist: 'xxx'"` 这个错误文本、**不去调官方**。
⇒ 产品那边的判据**一个字不用改**，`except ToolError` 分支照旧生效。
**已实测**：修好后 `restore=true` 正常返回，且 warnings 里**没有**"读不到 `UEMCP_env/`"那条
（= 产品确实认了这个文本、走了"不存在=正常"）。

⚠ **一个我走过的弯路，照实记**：我一度把 `except Exception` 改成 `except BaseException`，
以为能兜住 —— **没兜住，因为那个错根本不在我们的 Python 帧里**。那个改动留着仍有用
（防 UE 抛非 `Exception` 的东西），但**它不是这个问题的解**。

### 12.4 ⚠ 两个坑（都是实测踩出来的）

1. **`.ps1` 必须存成 UTF-8 with BOM** —— Windows PowerShell 5.1 读**无 BOM** 的 `.ps1` 会按

2. **脚本末尾要显式 `exit 0`** —— 同步/部署路径的最后一条外部命令是 `robocopy`，
   **成功时返回 1~7**，会被继承成脚本退出码。**实测两次**：打包明明成功、退出码却是 1
   —— 那会骗到 CI 与上架脚本。（`-Check` 有自己的 exit 0/1，不受影响。）

## 14. 干净工程 + 完整流程验证，抓到的**产品 bug**（2026-10-11）

### 14.1 `get_plan()` 阶段五假阳性

**现象**：在一个**全新工程（什么都没做）**里，`get_plan().stages` 的第 ⑤ 行报 **「进行中」**，
依据写着「`config/surface_materials.json` 有 create 11 个键」。

**判据（代码原话，`main.py` 原 10549 行）**：

```python
if n_mrows:            # 材质清单有行 → 按实例数判
    ...
elif n_cre or made5:   # ← 这里
    s5 = STAGE_STATE_DOING
else:                  # ← 事实上的死代码
    s5, e5 = STAGE_STATE_NOT_STARTED, ...
```

`n_cre` = **出厂配置** `config/surface_materials.json` 的 `create` 段配方条数（本包 11 条）。
**那不是"用户做了多少"的证据，是配置。** ⇒ 全新工程必然落进"进行中"，
**`else`（未开始）这支在真实安装里永远走不到**。

**修法（一行）**：`elif n_cre or made5:` → **`elif m_doc or made5:`**
（`m_doc` = 材质清单文件在、也解析得动，哪怕 `items` 是空的 —— 和 `made5` 一样都是**做过的产物**）。
清单**在磁盘上但读不动**时 `m_doc` 为假 → 仍走 else，而 `_m_state` 里那句
「⚠ 材质清单读不动…」照旧带出来（口径：**读不到 ≠ 没有**）。

**影响面**：只影响 `get_plan().stages` 里 ⑤ 那一行的**状态与依据**；
**不碰几何、不碰任何闸门**；服务器版与插件版同一份代码，一起修。
预检 ⑩ 只钉结构（8 条 / 编号 / 四个键 / 状态取值合法），**没有钉这一条语义** ⇒ 修完预检照样绿。

### 14.2 这一条是怎么被抓到的 —— 值得记

**不是**在开发机上发现的（那边阶段一~四都进行过，⑤ 本来就该是"进行中"）。
是**插件版在干净工程里跑 `get_plan`**，把一份"全未开始"的报文摆出来，那唯一一个"进行中"才显眼。

⚠ 而且**新对话的 agent 一度替它圆场**（原话大意：「实际还没有材质清单，符合预期，不用管它」）——
**"看起来合理"和"判据是对的"是两件事**。要不是逐行核代码，这条会一直躺着。
